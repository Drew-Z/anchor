# Anchor 持续开发主任务

主任务 ID：`anchor-development-loop`。建立于 2026-09-08。

目标：根据当前代码、可复现问题和验收证据，选择下一项有价值的本地开发子任务；完成并验收后，立即重新分析项目，选择下一项，持续推进 Anchor Learning / 锚学。

本文件定义重复执行的规则。[CURRENT_STATE.md](CURRENT_STATE.md) 是唯一的运行指针，保存当前阶段、唯一活动 leaf、验收结果和下一次决策。[NEXT_STEPS.md](NEXT_STEPS.md) 只保留队列摘要和发布边界，不另建一份独立状态。

## 与 Trellis 和手动继续的关系

复用 [Trellis execution map](trellis-execution-map.md) 的 `Root Goal → Branches → Leaves → Acceptance Gates` 方法。该历史文档不是正在运行的调度器。本主任务由当前 Codex 任务执行；用户于 2026-09-08 取消自动唤醒，后续通过当前任务中的直接消息继续。

正常执行期间，一个 leaf 通过验收后直接返回主任务分析，不需要用户逐项发送“继续”。会话结束或中断后，在收到用户消息时读取运行指针恢复；不创建定时唤醒，也不需要每完成一项就新建聊天、代理或 checkout。

这套流程可以保存进度并恢复；电脑关机、桌面应用未运行、目录不可访问、服务限流或断网时，无法保证即时执行。恢复运行后先核对实际状态，不把中断当成完成。

## 每次进入主任务

1. 读取根目录 [AGENTS.md](../AGENTS.md)、本文件和 `CURRENT_STATE.md`，遵守用户更新后的范围与约束。复用规范 checkout `D:\workspace4Cursor\learn\anchor`。
2. 核对分支、HEAD、工作区差异和仍在运行的本任务命令。只读检查应排除凭据、签名材料、参与者回答和两份受保护的用户验收报告。
3. 若存在未完成 leaf，先核对它的修改与已有证据，从缺失步骤恢复；不重复创建、不覆盖未知修改、不把全部差异自动暂存。若由其他活动任务持有这些文件，先避免重叠写入。
4. 没有活动 leaf 时，基于代码入口、失败检查、实际画面或明确需求，形成至多三个候选。每个候选写明证据、用户影响、工作范围和验收方式；未核实的猜测只能先安排有边界的调查。
5. 按优先级选择一个 leaf：数据或可靠性问题、阻塞核心流程的问题、可访问性和交互缺陷、影响后续判断的文档偏差。已有验收不充分的改动优先补齐。不要把已标为历史的待办重新激活。
6. 在 `CURRENT_STATE.md` 写入 leaf 契约及 `implementing` 状态后再编辑。一次只执行一个 leaf，所有实现、取舍、review 和最终验证由 Codex 主代理负责。

## Leaf 契约

每个 leaf 必须记录：

- ID 与目标：一个可完成、可验收的问题。
- 输入：具体代码、复现步骤、截图或已有检查结果。
- 输出：完成后可观察到的行为或可核对的文档事实。
- 拥有文件：准备修改的精确路径；新发现需要扩展范围时先更新契约。
- 验收：针对性检查、相应完整检查，以及必要的真实 UI 验收。
- 状态、基线提交、已完成步骤、剩余步骤、临时材料与恢复指针。

正常状态转换：`analyzing → implementing → verifying → analyzing`。leaf 只有在所需验收完成后才能记录为 `completed`。`waiting_external` 表示当前没有可独立推进的工作，需要外部证据或用户明确授权；它不是验收通过。

## 实现、验收与再次分析

1. 先亲读将修改的代码。对明确回归增加能在原实现失败、修复后通过的检查；不为简单文档调整或实现细节堆砌测试。
2. 完成聚焦修改，把状态写成 `verifying`。Flutter 行为修改运行针对性测试、相关完整测试、分析、格式检查和 `git diff --check`。App UI 修改还须在真实 Android 模拟器检查正常字号及窄屏大字号，验证操作并保存截图，最后恢复临时显示设置。
3. Web 行为修改运行本地 Web 检查，避免误用线上 base URL。文档修改核对声明对应的代码、链接和差异即可；若代码未变且基线证据仍适用，不重复运行整套 Flutter/Web 检查。
4. 分别记录通过、失败、未运行和证据范围。fixture、模拟器、真实模型、真机及远端 CI 不能互相替代。失败时修复本 leaf 或记录原因，不能悄悄降低验收标准。
5. 核对工作区差异，清理仅本轮新建且已无用途的临时文件；保留用户文件和归属不明的材料。按项目约定只对拥有的文件做小范围本地提交，保留提交 ID 和验收结果。
6. **完成后立即重新进入主任务步骤 2–5**：结合新结果重排候选，更新下一 leaf 的契约并继续执行。不要机械照搬初始清单；新证据可以改变优先级。

## 中断与等待

- 在开始耗时检查、工具返回仍在运行、发现阻塞、完成 leaf 时及时更新运行指针。未完成的构建或测试须确认退出状态后才能记为通过。
- 遇到中断先查看已有修改、日志和对应进程，再决定续等、重跑缺失检查或继续实现；不能重做已完成 leaf。
- 同一失败在条件未变时不得无限重试。记录命令、原因及恢复条件；有独立可推进的候选时返回主任务选择它。
- 没有新代码、没有可行动的新证据、只剩外部阻塞时进入 `waiting_external`。之后收到用户消息再核对相关条件，不能反复全量测试、空提交或凭空制造新功能。
- 用户要求停止或暂停时，更新运行指针并停止本轮执行。自动唤醒已取消，不得用新自动化或后台 runner 恢复它。

## 持续授权边界

用户已授权项目分析、本地实现、检查、验收、本地提交以及本任务的持续推进。每个普通 leaf 不再单独索取确认。

推送、合并 PR、生产部署、创建发布、签名或分发 APK、可选 cohort 研究和发布验收等事项仍按根 `AGENTS.md` 及当前发布文档处理。连续开发不自动授权向他人发送消息、操作真机设置或处理机器级凭据。

历史 Claude 任务、外部任务日志及保留 worktree 仅用于必要的历史查询。不要恢复旧代理、旧 runner、网络健康探针或旧执行队列。

## 调度状态

当前为手动继续模式。应用已确认原 `anchor` 自动化不存在；其历史迁移和取消结果记在 `CURRENT_STATE.md`。完成 leaf、重启桌面应用或遇到外部阻塞都不构成重新启用自动化的授权。

只有用户以后明确要求恢复自动唤醒时，才重新配置调度并验证实际结果。项目推进和 leaf 的完成判定仍按上述流程执行。
